# Calculation state, overview camera and apex refinement

Calculate lines previously called the full selection flow: it cleared the map, hid the width form and fitted the whole track from draw(), even though a later applyView call requested viewport preservation. Generated overlays also remained off. Recalculation now retains the current result, form, focus and viewport while the worker runs. The button reports progress and prevents duplicate submissions. A successful user calculation displays all three generated lines. An unsuccessful recalculation keeps the previous result and rolls back the session's accepted width. Reset returns to the dataset's default/unavailable state. Source GeoJSON remains unchanged. The 3D view can also rebuild its geometry without fitting its camera again.

The world overview records its last centre and zoom when a track is opened. Browser Back and Explore world map restore that camera. Reset view still fits the current catalogue/track normally.

The reported Smolensk and Ahvenisto corners exposed a solver limitation. Minimum curvature can favour a large outer radius around an entire hairpin. The old small-patch stage could not move far enough inward, and coarse candidate ranking could reject improvements to the actual dense model. The corrected optimizer compares feasible curvature/distance seeds, tests larger and smaller patches centred on actual turns, and uses the dense vehicle model throughout. It does not force every corner to an artificial apex waypoint.

Both displayed edge arrays are now explicit feasibility inputs. Signed clearance is evaluated against the paired runtime edge segments, and a 4.6 × 2.05 m body is checked at sampled positions and intermediate quarter steps with the 0.1 m side margin plus a numerical buffer. Nearby source stations identify the correct road visit at a bridge. A centreline offset alone is no longer the final containment test.

Time-refinement windows extend 350 m beyond the changed geometry. Their entry/exit speeds join the current feasible profile; padded neighbouring geometry supplies the actual 3 m curvature window. A candidate that cannot join is rejected. Whole-route precise speed solves certify each sweep, with rollback if a sweep worsens the previous whole-route time. Safeguarded Newton solves accelerate the same speed constraints and are checked against precise bisection. Streaming physical-window interpolation agrees exactly with the prior binary lookup in focused tests. These changes avoid a coarse-time veto while keeping on-demand calculation practical.

This remains an independent constrained point-mass approximation, using TUM's curvature/time-optimization concepts. It does not run TUM's upstream CasADi/IPOPT double-track minimum-time solver. GT3 parameters, constant-width boundaries and absent banking remain assumptions. Numerical feasibility and a faster simulated lap do not establish the real fastest line or surveyed track accuracy.

Sixteen focused tests pass, including the two reported west-side corners, including both Smolensk layouts, inward apex placement, all sampled/intermediate body envelopes against actual paired edges, speed-root equivalence, fixed-speed window joins, bridge visit separation, model response and source-only GeoJSON. Four browser tests pass against the built preview, covering zoom, in-place recalculation, automatic line display, failed recalculation preservation, disclaimer, world-map camera restoration, search and outline loading. The Calculate lines button was also pressed manually through the shared preview to reproduce and verify the reported issue. No new satellite imagery or database-wide imagery validation was used.

The current local runs calculate Smolensk/Ahvenisto in roughly 3–4 seconds and Nordschleife BTG in roughly 30 seconds, cached in the page session. These are machine-specific prototype timings. Evidence is in .local/apex-fix/ and .local/ui-followups/. Only the persistent Tailscale preview is updated; production is unchanged.
